## Esito

**Da correggere.** L'impianto è buono: token da 192 bit, solo l'hash nel database, ruoli controllati sul server, 404 uniformi, IDOR chiusi su `inviteId`, `channelId` e `userId`. C'è però un problema bloccante: la revoca promessa dall'interfaccia non è disponibile appena si chiude il dialog, quindi un link finito nelle mani sbagliate resta valido e riusabile per 7 giorni. ## Problemi

### Bloccante

**B1. Un invito non si può più revocare dopo aver chiuso il dialog**
`app/client/src/components/invite-dialog.tsx:62-68` e `:79`; `app/server/routes.ts` (manca un `GET /api/workspaces/:workspaceId/invites`).

Il dialog dice "Il link vale 7 giorni e puoi revocarlo in qualsiasi momento", ma l'unico modo di revocare è il pulsante che compare subito dopo la creazione. `handleOpenChange(false)` fa `create.reset()` e l'`id` dell'invito si perde. Il server non ha nessuna route che elenchi gli inviti, quindi né il client né l'admin possono più ritrovarlo.

Scenario: l'admin incolla il link in un canale sbagliato o in una mail inoltrata, chiude il dialog e se ne accorge dopo. Il link è multiuso, senza limite di utilizzi, e per 7 giorni chiunque abbia un account può entrare, leggere i canali pubblici e #general, vedere nome ed email di tutti i membri e scrivere loro in DM. L'unico rimedio è una `UPDATE` a mano sul database. La revoca è il controllo che rende accettabile un link multiuso: se non funziona, il rischio del link diventa quello di un segreto permanente per una settimana.

Correzione proposta: una route di elenco per owner/admin e la lista nel dialog, ognuna con il suo "Revoca".

```ts
// storage.ts
async listActiveInvites(workspaceId: string) {
    return db
        .select({
            id: workspaceInvites.id,
            createdAt: workspaceInvites.createdAt,
            expiresAt: workspaceInvites.expiresAt,
            uses: workspaceInvites.uses,
            createdBy: { id: users.id, name: users.name },
        })
        .from(workspaceInvites)
        .innerJoin(users, eq(workspaceInvites.createdById, users.id))
        .where(
            and(
                eq(workspaceInvites.workspaceId, workspaceId),
                isNull(workspaceInvites.revokedAt),
                gt(workspaceInvites.expiresAt, new Date()),
            ),
        )
        .orderBy(desc(workspaceInvites.createdAt));
}

// routes.ts: stesso controllo del ruolo della POST; mai restituire token_hash
app.get("/api/workspaces/:workspaceId/invites", authenticateToken, async (req, res) => {
    const role = await storage.getWorkspaceRole(req.params.workspaceId, req.user!.id);
    if (!role) return res.status(404).json({ message: "Workspace not found" });
    if (!canManageWorkspace(role)) return res.status(403).json({ message: "Forbidden" });
    res.json(await storage.listActiveInvites(req.params.workspaceId));
});
```

In alternativa minima, se la lista slitta: togliere "puoi revocarlo in qualsiasi momento" e accorciare la durata. Ma la lista è la correzione giusta, e serve anche a vedere quante persone sono entrate con ciascun link (`uses`).

### Da correggere

**D1. Il token dell'invito finisce in chiaro nei log**
`app/server/index.ts:34`, con le route `app/server/routes.ts:631` e `:648`.

Il logger registra `req.path`, e per gli inviti il percorso è il token: `GET /api/invites/<token>` e `POST /api/invites/<token>/accept`. La prova lo mostra nel log del server. Lo schema salva solo l'hash proprio perché "chi legge la tabella non può usare gli inviti" (`shared/schema.ts:142-145`), ma chi legge i log (pannello dell'hosting, aggregatore, backup dei log, un collaboratore con accesso alla console) ottiene token validi per 7 giorni e, con B1, non revocabili.

Correzione proposta: mascherare il token nel logger, così vale per tutte le route presenti e future.

```ts
// index.ts
const SECRET_SEGMENTS = [/^(\/api\/invites\/)[^/]+/];
const redact = (p: string) =>
    SECRET_SEGMENTS.reduce((acc, re) => acc.replace(re, "$1[token]"), p);
// ...
log(`${req.method} ${redact(path)} ${res.statusCode} in ${Date.now() - start}ms`);
```

Più robusto ancora: passare il token nel corpo (`POST /api/invites/lookup` e `POST /api/invites/accept` con `{ token }`), che il logger già non registra. Se in produzione c'è un proxy davanti all'app che registra l'URL completo, solo lo spostamento nel corpo risolve.

### Minori

**M1. Corsa tra revoca e accettazione**
`app/server/routes.ts:653-662`, `app/server/storage.ts:251-317`.

L'accettazione legge l'invito (`getValidInvite`), poi in un'altra istruzione inserisce il membro (`joinWorkspace`, transazione separata), poi conta l'uso. Nessun lock tiene ferma la riga dell'invito. Nella prova, con 8 accettazioni in parallelo e una revoca, un utente è entrato 31 ms dopo il commit della revoca, e `uses` è salito su un invito già revocato. La finestra è piccola e l'attaccante deve sapere quando parte la revoca, quindi l'impatto pratico è basso; ma la revoca è il freno di emergenza e conviene che sia netta.

Correzione proposta: un unico metodo transazionale che blocca la riga dell'invito. In `READ COMMITTED`, `SELECT ... FOR UPDATE` aspetta la revoca in corso e poi rivaluta la condizione sulla versione aggiornata della riga.

```ts
async acceptInvite(tokenHash: string, userId: string) {
    return db.transaction(async (tx) => {
        const [found] = await tx
            .select({ invite: workspaceInvites, workspace: workspaces })
            .from(workspaceInvites)
            .innerJoin(workspaces, eq(workspaceInvites.workspaceId, workspaces.id))
            .where(and(
                eq(workspaceInvites.tokenHash, tokenHash),
                isNull(workspaceInvites.revokedAt),
                gt(workspaceInvites.expiresAt, new Date()),
            ))
            .for("update", { of: workspaceInvites });
        if (!found) return undefined;
        const joined = /* insert in workspace_members + #general con tx, come joinWorkspace */;
        if (joined) {
            await tx.update(workspaceInvites)
                .set({ uses: sql`${workspaceInvites.uses} + 1` })
                .where(eq(workspaceInvites.id, found.invite.id));
        }
        return { ...found, joined };
    });
}
```

Nello stesso giro, `revokeInvite` (`storage.ts:308-317`) dovrebbe aggiungere `isNull(workspaceInvites.revokedAt)` alla condizione: oggi una seconda revoca risponde 204 e sovrascrive `revoked_at`, perdendo l'ora della revoca vera.

**M2. Il filtro di `next` si aggira con tabulazioni e a capo**
`app/client/src/lib/redirect.ts:7`, usato in `app/client/src/pages/auth.tsx:36`.

`useSearch` di wouter applica `decodeURI` alla query e poi `URLSearchParams` decodifica di nuovo. Con `?next=/%09/evil.com` il valore è `"/\t/evil.com"`: comincia con `/`, non con `//`, e passa. Il parser URL del browser toglie tabulazioni e a capo e lo legge come `//evil.com`, cioè `https://evil.com/`. Oggi non diventa un open redirect perché wouter naviga con `history.replaceState`, che rifiuta un URL di un'altra origine con `SecurityError`. L'effetto attuale è solo un errore non gestito nella pagina di login. Ma il filtro dà una falsa sicurezza: basta passare a `window.location.assign` o a un redirect lato server e diventa sfruttabile per phishing ("accedi per entrare nel workspace" e poi via su un sito falso).

Correzione proposta: decidere con il parser del browser, non con controlli sulla stringa.

```ts
export function safeNextPath(search: string): string {
    const next = new URLSearchParams(search).get("next");
    if (!next) return "/";
    try {
        const url = new URL(next, window.location.origin);
        if (url.origin !== window.location.origin) return "/";
        return url.pathname + url.search + url.hash;
    } catch {
        return "/";
    }
}
```

**M3. Scadenza calcolata con il fuso della sessione Postgres**
`app/shared/schema.ts:159-160`, `app/server/storage.ts:295` e `:311`.

`expires_at` è `timestamp` senza fuso. Drizzle scrive il `Date` di JavaScript come ora UTC, ma `getValidInvite` lo confronta con `now()`, che è `timestamptz` e converte la colonna con il fuso della sessione. Il container locale è in UTC e tutto torna; su un database con fuso `Europe/Rome` un invito scade un'ora prima (provato: a 30 minuti dalla scadenza risulta già scaduto), con un fuso americano dura ore in più del previsto. `revoked_at = now()` invece viene salvato nel fuso della sessione, quindi le due colonne non sono confrontabili tra loro.

Correzione proposta: confrontare con un parametro JavaScript, `gt(workspaceInvites.expiresAt, new Date())`, e salvare la revoca con `revokedAt: new Date()`. Meglio ancora, per le colonne nuove, `timestamp(..., { withTimezone: true })`.

**M4. Chiunque abbia il link vede le email di tutti i membri**
`app/server/routes.ts:663-669` (`member:joined`), `app/server/storage.ts:62-71` (`publicUserColumns`).

Non è un difetto introdotto da questa PR: `GET /api/workspaces/:id/members` restituiva già le email. Ma con gli inviti a link chiunque riceva il link (anche inoltrato) entra e ottiene le email di tutto il workspace, e l'evento `member:joined` manda a tutti l'email del nuovo arrivato. In un'app che si presenta come chat di team è un dato personale (GDPR) che non serve all'interfaccia: il dialog dei membri mostra solo nome e avatar.

Correzione proposta (anche in un'issue separata): un `memberUserColumns` senza `email` per tutto ciò che riguarda altri utenti (membri del workspace e del canale, eventi WS, `sender`/`receiver` dei messaggi), lasciando l'email solo in `/api/auth/me`.

**M5. La presenza non arriva nel workspace appena raggiunto**
`app/server/routes.ts:172` e `:648-678`.

`userWorkspaces` si riempie solo all'apertura del WebSocket. Dopo un'accettazione il nuovo workspace non viene aggiunto, quindi alla disconnessione gli altri membri non ricevono `presence:update` e vedono l'utente "online" finché non ricarica. Non espone dati; è un'incoerenza di stato che conviene chiudere nello stesso punto (`userWorkspaces.get(req.user!.id)?.add(found.workspace.id)` dopo il join).

**M6. Referer sulla pagina dell'invito**
`app/client/index.html`. La pagina `/invito/<token>` carica Google Fonts. Con la politica predefinita dei browser attuali (`strict-origin-when-cross-origin`) esce solo l'origine, quindi oggi il token non trapela. Come difesa in profondità, `<meta name="referrer" content="no-referrer">` nella pagina dell'invito o un header `Referrer-Policy` (che arriverà con helmet, #13).

## Punti verificati e corretti

- **Token**: `randomBytes(24)` in base64url, 192 bit di entropia; nel database solo SHA-256 con indice unico. Per un segreto casuale così lungo l'hash senza sale è adeguato, e il confronto avviene sull'hash dentro Postgres, quindi non c'è un confronto a tempo variabile sul token. Il token in chiaro esce una sola volta, nella risposta della creazione.
- **Ruoli**: creazione e revoca controllano `owner`/`admin` sul server; il client nasconde la voce di menu solo per comodità. Un non membro riceve 404 sia su un workspace vero sia su uno inesistente.
- **IDOR**: `revokeInvite` filtra per `id` e `workspaceId` insieme; `channelId` passa sempre da `getAccessibleChannel`; il `userId` da aggiungere deve essere membro dello stesso workspace del canale ed è validato come UUID.
- **Canali privati**: un membro del canale può aggiungere qualsiasi membro del workspace, come voluto; un non membro non vede né la lista né il canale (404). `channel:added` arriva solo alla persona aggiunta, che da quel momento ha diritto a vedere il canale.
- **Join**: `onConflictDoNothing` sull'indice unico `(workspace_id, user_id)` rende l'accettazione idempotente e impedisce di declassare un owner a `member`; membro e #general sono nella stessa transazione.
- **DM e typing**: `shareWorkspace` risponde 404 identico per utente inesistente e per utente senza workspace in comune, e il typing verso estranei viene scartato in silenzio: niente enumerazione degli utenti per UUID.
- **CSRF**: l'accettazione richiede l'header `Authorization`, non un cookie, e un clic esplicito sulla pagina dell'invito.
- **Navigazione client**: il token nel percorso non può contenere `/`, `?` o `#` (wouter non decodifica i caratteri riservati), quindi non si possono deviare le chiamate `fetch` verso altre route.
